# Приложение «Аналитика CRM» — краткое описание

## Назначение и реализованные сценарии

Web-приложение на платформе VibeCode (Битрикс24), встроенное в портал. Показывает
аналитику по сделкам CRM. Реализовано три блока:

1. **Сводка по стадиям воронки** — количество сделок и их сумма по каждой стадии
   (`stageId`); выигранные и проваленные стадии выделены цветом.
2. **Ключевые показатели (KPI)** — сумма открытых сделок за период, количество
   выигранных сделок за период и средний чек выигранных.
3. **Последние сделки** — до 15 сделок за период: название, сумма, стадия и ответственный,
   с переходом в карточку сделки.

Есть **фильтр по периоду**: пресеты 7/30/90 дней и «этот месяц» плюс произвольные даты
«с/по» (валидируются на сервере, формат `YYYY-MM-DD`). Пресета «Всё время» нет: на порталах
с более чем ~5000 сделок агрегация без фильтра по дате возвращает `AGGREGATION_LIMIT_EXCEEDED`,
поэтому применяются периоды с фильтром по дате.

## Модель доступа и запрошенные скоупы

Реализован **Путь А — «от лица авторизованного пользователя»** (accessPolicy **`oauth_app`**).
Каждый портальный вызов идёт с личностью посетителя из заголовков шлюза:
`Authorization: Bearer <X-Vibe-Authorization>` + ключ приложения (`X-Api-Key`). Без сессии
приложение отвечает `401 no_session`. Данные кешируются **по пользователю** (`userId:period`),
а имя посетителя показывается в шапке (из `X-Vibe-User-Name-Encoded`).

Запрошенные скоупы рабочего ключа и обоснование:

- **`crm`** — чтение сделок (`/deals/aggregate`, `/deals/search`): обязательное право для
  всей аналитики.
- **`user`** — чтение справочника сотрудников (`/users`) для имён ответственных.
- **`placement`** — для встройки приложения в портал (пункт меню / вкладка).
- Ключ **read-only** (`READONLY`): приложение ничего не пишет.

## Известные ограничения

- Портал отвечает десятки секунд — данные собираются в фоне и кешируются по пользователю
  с подписью «обновлено N минут назад».
- Нагрузки обрабатываются: внутри `portal()` выполняется повтор на `429` (пауза из
  `Retry-After`, до 3 попыток); после ошибки сборки снимка — пауза `SNAPSHOT_RETRY_MS`
  (~45 c) до следующей попытки; кнопка «Обновить» форсирует пересборку даже без данных
  (с cooldown).
- KPI суммируются по полю `amount` в исходной валюте и выводятся как рублёвые; у отдельных
  сделок валюта показывается из поля.
- Период «Всё время» не поддерживается на порталах с >~5000 сделок (лимит агрегации).

## Инструкция для проверяющего

1. Ключ приложения **`vibe_app_`**, политика **`oauth_app`**, права **`crm`**, **`user`**,
   **`placement`** (read-only). Подтверждение — `GET /v1/me` рабочего ключа: должно быть
   `oauth_app`, `READONLY`, `crm`, `user` и `placement` при встройке.
2. Опубликовать приложение (кнопка «Деплой» в карточке «Приложение»).
3. Открыть приложение **из портала Битрикс24** (встроенный пункт меню / вкладка) — в шапке
   появится имя вошедшего; проверить воронку, KPI и список сделок, переключить период.
4. Вне портала `/api/dashboard` отвечает `401 no_session` — это норма для Пути А.
5. Тест обработки 429: `npm test` («один 429 → после паузы данные есть»).
