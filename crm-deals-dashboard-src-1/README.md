# CRM-дашборд «Аналитика сделок»

Web-приложение на платформе VibeCode (Битрикс24), встроенное в портал. Показывает
аналитику по сделкам CRM: воронку по стадиям, ключевые показатели и список последних
сделок. Данные читаются из подключённого портала через REST-прокси.

## Модель доступа (Путь А — «от лица пользователя», accessPolicy `oauth_app`)

Приложение работает **от лица авторизованного пользователя портала**. Каждый портальный
вызов выполняется с личностью посетителя: в заголовки, помимо ключа приложения
(`X-Api-Key: <BITRIX_API_KEY>`), добавляется
`Authorization: Bearer <X-Vibe-Authorization>`, где `X-Vibe-Authorization` — личность
посетителя из заголовков шлюза.

- **401 без сессии**: если шлюз не прислал личность (`X-Vibe-User-Id` / `X-Vibe-Authorization`),
  дашборд отвечает `401 no_session` и просит открыть приложение из портала.
- **Кэш по пользователю**: снимки и справочники кешируются отдельно для каждого
  пользователя (ключ `userId:period`), чтобы данные одного посетителя не «протекали» другому.
- **Имя в шапке посетителя**: имя берётся из заголовка `X-Vibe-User-Name-Encoded` и
  отображается в шапке дашборда.

Для работы нужен ключ приложения типа **`vibe_app_`** с политикой **`oauth_app`**
(подтверждение — `GET /v1/me` рабочего ключа). Приложение только читает данные, ничего
не пишет.

## Назначение и реализованные сценарии

1. **Сводка по стадиям воронки** — количество сделок и их сумма по каждой стадии
   (`stageId`); выигранные и проваленные стадии выделены цветом.
2. **Ключевые показатели (KPI)** — сумма открытых сделок за период, количество
   выигранных сделок за период и средний чек выигранных.
3. **Последние сделки** — до 15 сделок за период: название, сумма, стадия и ответственный,
   с переходом в карточку сделки.
4. **Фильтр по периоду** — пресеты 7/30/90 дней и «этот месяц» плюс произвольные даты
   «с/по». Период валидируется на сервере (только `YYYY-MM-DD`) и применяется к каждому блоку.
   Пресета «Всё время» нет: на порталах, где сделок больше ~5000, агрегация без фильтра по
   дате возвращает `AGGREGATION_LIMIT_EXCEEDED`, поэтому главный экран открывается за
   последние 30 дней.

## Запрошенные скоупы и обоснование

- **`crm`** — чтение сделок (`/deals/aggregate`, `/deals/search`): обязательное право для
  всей аналитики.
- **`user`** — чтение справочника сотрудников (`/users`): имена ответственных по делам.
- **`placement`** — для встройки приложения в портал (пункт левого меню / вкладка).
- Ключ **read-only** (`READONLY`): приложение ничего не создаёт и не меняет.

## Известные ограничения

- Портал отвечает десятки секунд, поэтому данные собираются в фоне и кешируются по
  `пользователь:период` с подписью «обновлено N минут назад».
- **Обработка 429 / нагрузок**: внутри `portal()` выполняется повтор на `429` с паузой из
  заголовка `Retry-After` (до 3 попыток); после ошибки сборки снимка делается пауза
  `SNAPSHOT_RETRY_MS` (~45 c) до следующей попытки, а кнопка «Обновить» форсирует
  пересборку (с `cooldown` от частых нажатий), в том числе когда данных ещё нет.
- На порталах с >~5000 сделок период «Всё время» не рассчитывается (лимит агрегации) —
  вместо него используются периоды с фильтром по дате.
- KPI суммируются по полю `amount` в исходной валюте и выводятся как рублёвые; у отдельных
  сделок валюта показывается из поля.

## Инструкция для проверяющего

1. В кабинете VibeCode создайте/привяжите ключ приложения **`vibe_app_`** с политикой
   **`oauth_app`** и правами **`crm`**, **`user`**, **`placement`** (read-only).
   Подтверждение политики — `GET /v1/me` рабочего ключа (в ответе должно быть
   `oauth_app`, `READONLY`, `crm`, `user`, при встройке — `placement`).
2. Опубликуйте приложение (кнопка «Деплой» в карточке «Приложение»).
3. Откройте приложение **из портала Битрикс24** (встроенный пункт меню / вкладка), будучи
   вошедшим в систему, — в шапке появится ваше имя.
4. Проверьте: воронку по стадиям, три KPI и список последних сделок; переключите период
   (7/30/90 дней, «этот месяц», свои даты).
5. Диагностика: `GET /api/health`; `GET /api/dashboard?preset=30d` (ответ `401 no_session`
    вне портала — это норма для Пути А).

## Тест

`npm test` — проверяет обработку перегрузки: «один `429` → после паузы данные есть»
(фейковый портал отвечает 429, `fetchWithRetry` пережидает и возвращает данные).
